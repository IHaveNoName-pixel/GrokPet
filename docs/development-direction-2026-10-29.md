# GrokPet 下一阶段开发方向

核对时间：2026-10-29。依据用户提供的计划、当前源码及项目验收记录。本轮重新运行 100 项单元测试，全部通过；检查的 10 个核心程序文件与当前 `dist/BlobPet-corner-stage` 运行包一致。本轮只分析并制定方向，未新增运行功能或重启程序。

## 1. 产品定位与计划调整

建议定位为 **有角色生命感的 Windows AI 工作伙伴**。以已有的 Codex、系统状态、音乐、下载及提醒联动为基础，增加可直接使用的助手入口，同时保留轻量养成。

用户提供的计划适合作为功能愿景，但不能直接当作开发任务表：它把已有能力重新列为待开发，也把语音、窗口吸附、泛化桌面控制等复杂事项放在了同一优先级。需要按现有依赖拆分。

新的开发顺序建议：**稳定性与命令基础 → 受控系统操作 → 按键语音与播报 → 可管理记忆 → 主动截图问答 → 更复杂的桌面任务**。投喂可作为中间的小功能版本交付；追球依赖窗口运动验收，安排在其后。插件市场、多宠物和任意桌面自动操作后置。

## 2. 当前能力与实际缺口

| 方向 | 当前已实现 | 尚缺什么 |
| --- | --- | --- |
| 基础桌宠 | 透明悬浮、拖动、托盘、隐藏、尺寸／颜色／身形、漫游、困倦睡眠、点击反馈 | 边缘吸附、攀爬、多宠物；真实多屏／系统 DPI 完整验收 |
| 角色状态 | 问答及任务阶段动作、音乐动作、下载／安装进度动作、低优先级负载动作 | 基于聊天语义的情绪表达；现有阶段动作不等于理解对话情绪 |
| AI 问答 | Codex、独立快捷和完整问答上下文、流式回复、停止、复制／查看／重显 | 持久陪伴记忆、独立人格提示、语音和图片输入 |
| API 配置 | 多配置、模型名称与地址、加密密钥、OpenAI 兼容文本聊天协议 | 不同真实服务的兼容验收、模型能力描述；不能据此声称所有模型都支持图片或工具调用 |
| 系统状态 | CPU／内存／GPU、网络速度、VPN／代理、最近一分钟趋势、持续负载阈值 | 电池、音量控制、常用应用启动等主动系统操作 |
| 效率工具 | 专注计时、免打扰、场景、提醒、重复提醒、待办、到期确认 | 专注计时跨重启恢复、日历集成、工作时间统计、便签；手动选择场景不等于自动识别环境 |
| 本地命令 | 明确格式创建提醒／待办、专注控制、音乐控制、显示卡片 | 统一命令注册、应用白名单、取消／结果反馈与语音共用入口 |
| 编程伙伴 | Codex 额度和 hooks 阶段状态；只读项目问答 | 通用 VS Code／Git／构建事件适配，以及跳转到确切工作界面 |
| 媒体及下载 | 网易云播放控制、本地 LRC／手动同步；浏览器桥接和下载器／安装适配器 | 音乐目前为原版循环 dictating，尚无真实频谱；浏览器、迅雷、安装完整生命周期仍需真实验收 |
| 养成 | 名字、活跃程度、可选作息、精力／心情／好感、抚摸收益和保存恢复 | 投喂、玩具、成长目标；现有数值不是跨会话的聊天记忆 |
| 通知 | Windows 新通知授权入口、气泡和专注时普通提示暂缓 | 每类提示的更细偏好；专注免打扰仅作用于桌宠 |
| 语音／桌面感知／插件 | 暂无生产功能 | 麦克风录音、STT、TTS、截图模型输入、技能执行协议 |

注意：存在 `capture-smoke.cjs` 等界面验收文件不代表已经实现“桌面截图问答”；项目含有 Cult UI 源文件也不代表所有组件都在当前运行界面使用。

## 3. 推荐里程碑及完成条件

### M1：稳定性及统一命令基础（P0）

**目标：现有功能稳定，并让下一阶段的文字、语音和按钮共用一套操作逻辑。**

- 保留现有 SVG 引擎和当前有效界面，不进行框架重写。逐步从 `main.cjs` 提取命令执行和动作选择逻辑，保持现有行为不变。
- 统一命令结构：命令 ID、参数校验、来源、请求 ID、执行结果、取消能力及所需授权。先迁移已有的提醒、专注、音乐和显示命令。
- 现有动作规则需有明确优先级、有效期及“正在播放该动作的原因”，便于排查暂停下载仍占据动作等问题。
- 收尾鼠标、滚动、输入法、四角、卡片快速开关、复位及 3 秒停留验收；实际第二显示器和 Windows 缩放作为单独的待验收项。
- 为专注计时保存状态和截止时间：运行中重启按真实时间恢复，暂停状态保持剩余时长；过期只提示一次。持久提醒逻辑继续复用。
- 统一正式入口、暂存构建、验收、备份与替换流程；更新旧文档中的测试数和功能状态，程序升级保留本机数据。

**完成条件**：原有命令行为不变；失败不进入伪成功状态；重启不丢计时；隐藏项无空位；发布可回滚；验收清楚区分模拟输入和真实设备操作。

### M2：Windows 常用操作（P1，先用文字入口交付）

**首批范围**：启动用户配置的应用／打开配置的文件夹、查询和调整主音量、播放暂停／切歌、查询系统状态、创建提醒和待办、控制专注计时。

- 应用通过设置页选择和命名，以白名单 ID 启动；不让模型返回任意 shell 或 PowerShell 文本执行。
- 明确命令走本地执行，不发送给聊天模型。歧义问题先展示候选目标；普通聊天沿用所选后端。
- 气泡展示执行结果或失败原因，提供必要的撤销／停止；文件整理、删除、关闭程序和系统电源操作不纳入首版。

**完成条件**：按钮和文字命令调用同一执行器；错误应用路径、执行失败、重复提交均有反馈；未配置应用不能被模型临时编造执行目标。

### M3：按键语音与 TTS（P1，下一阶段主要体验目标）

**第一版体验**：点击麦克风或按配置快捷键 → 录音 → 显示识别文本 → 本地命令执行或发给模型 → 气泡回复，可选语音播报。先提供清晰的按键交互，唤醒词和持续监听后置。

- 使用明确的录音中状态，允许取消；权限拒绝、无设备、空识别、超时都能退回文字输入。
- 识别后的不确定文本先允许修改；系统命令使用 M2 的相同校验和授权规则。
- STT／TTS 后端与现有文本模型配置分开，说明网络使用及服务计费；先完成一个后端的真实设备验证，再扩展其他后端。
- 可停止播报，新一轮录音时中断播报，避免把自身声音录成指令；长回答限制播报长度，代码默认不逐字朗读。
- 动作可使用 listening（就绪）、dictating（录音）、loading（连接）、thinking（回答生成）、receiving（接收）、humming（播报），并遵守停止与超时逻辑。

**完成条件**：真实麦克风上完成“语音创建提醒”“普通聊天并播报”“取消录音”“打断播报”；断网或服务失败不误执行命令；不录音时没有后台采集。

### M4：陪伴记忆与轻量互动（P1/P2）

- 新增独立的本地记忆存储，先支持用户明确说“记住”的称呼／偏好；提供查看、编辑、删除、清空和禁用。
- 把日常陪伴记忆与只读项目问答隔开，按需提供相关事实；删除后不再注入新请求，并提供重开当前会话的入口。
- 在模型支持的条件下，增加白名单情绪提示：happy、curious、confused、sad 等，短时播放后退回当前活动；不允许模型借情绪标记触发系统操作或直接改变长期好感。
- 投喂先复用现有养成系统，限制频率、显示即时反馈；追球在移动与边缘验收后加入。无需先扩展衣柜、经济或复杂升级系统。

**完成条件**：记忆可控且不会串入其他入口；情绪异常输出可降级；投喂收益有上限，任务进行时不会被互动动画长期覆盖。

### M5：主动桌面感知（P2）

- 用户主动选择区域或窗口，先预览截图，再决定是否发给支持图片的模型。
- 首批只做“解释错误”“解释当前截图”“翻译用户提供的文字”，不持续观察屏幕。
- 图片能力单独检测，当前文本 API 不能默认承诺支持；失败和取消均删除待发送状态。

**完成条件**：无主动操作不采集；发送范围可见；不支持图片的配置有明确提示；模型看到的内容不会自动变成系统命令。

## 4. 架构演进方向

保留 Electron 主进程、原生 Windows 桥接、现有 SVG 角色及现有独立问答会话。以小步提取模块的方式演进：

- **输入层**：快捷气泡、完整问答、按钮，后续增加语音和用户提供的截图。
- **命令层**：已有明确本地命令与受控系统操作，独立于模型服务。
- **对话层**：现有 Codex／API 适配器；后续补能力检测、人格提示和受控记忆注入。
- **动作层**：集中仲裁当前交互、任务、音乐、专注、提醒与养成，避免各功能长期锁定动作。
- **存储层**：设置、提醒、专注恢复、养成、记忆各有清晰范围，升级有版本和迁移验证。

先使用内部的命令注册表。插件加载、签名／许可、安装更新和权限管理尚无基础，不宜直接扩展为插件市场。

## 5. 下一轮实际开发清单

建议下一轮只执行 M1，并交付可复用的基础：

1. 明确卡片的点击／悬停／拖动状态，补齐可执行的回归矩阵。
2. 提取统一命令执行器，接回已有提醒、音乐、专注与卡片开关。
3. 增加专注计时跨重启恢复与去重完成提醒。
4. 固定唯一运行入口，整理验收和回滚记录。

随后执行 M2，再接 M3 的真实麦克风闭环。投喂可作为 M1 后的小功能版本穿插；追球保持后置。这样既延续原来的宠物路线，也为这份新计划中的语音助手打下基础。

## 6. 本轮判断的边界

100 项测试通过说明当前自动化回归通过，不等于所有真实软件和设备已验收。本轮没有重新验收麦克风、多屏、实际系统缩放或所有下载器。文档中的第三方项目和图片只作为用户提供的愿景材料，本轮未核验其功能、维护状态或许可，不据此宣称已经选型。后续选择具体语音／模型／系统 API 时，再对照官方文档进行验证。
