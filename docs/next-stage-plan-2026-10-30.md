### 1. 先修复通知投递完整性

源码发现：main.tick 从 Companion.nextNotice() 取走通知后发送给渲染端；pet.js 的 say() 会在聊天保护时直接返回。普通通知因此存在被消费但未显示的路径。应在队列消费之前决定暂缓，或建立可确认投递机制，而不是仅在渲染端忽略。复用现有 NoticeQueue 的有界队列、去重和专注规则，补足过期与确认投递，防止完成聊天后集中刷屏。

验收：思考中、流式回复、答案保护期、停止和失败分别插入普通/重要提醒；确认普通通知不会丢失、重要提醒及时显示、旧通知不重复播放。

### 2. 工作卡片复用现有服务

复用 Companion.snapshot.work / projects，不增加 Git 轮询器或动画调度器。先把已有信息变成日常可见的入口。未登记、监测关闭和状态未知应明确显示；无任务不占空位。选择“查看项目”与“把项目作为问答参考”是两种不同操作。

### 3. VS Code 接入边界

扩展只发送工作区身份、会话 ID、诊断数量、调试状态和心跳。默认不传代码、文件全文、终端正文或完整诊断描述。桌宠端校验本机鉴权、消息大小、字段和已登记根目录，用户可解绑/撤销；配对凭据不进日志。

当前 WorkEvent 类型主要表达 turn/tool，需要为诊断、调试和心跳设计准确的摘要事件或状态适配，不能伪装成 Codex 工具事件。事件仍归于既有工作中心；动画继续由原调度器仲裁。新增诊断不直接等于任务失败，关闭调试不等于任务成功。

优先验证：真实 VS Code 窗口 → 制造/修复诊断 → 开始/停止调试 → 关闭窗口后过期 → 重连；同时打开两个仓库，状态不串项目。首批不扩展到 Visual Studio、JetBrains 或插件市场。
